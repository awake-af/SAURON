# SAURON — runbook по фазам

Документ описывает порядок работ: от выбора Oracle Always Free как «мастер»-площадки до автоматизации failover через DNS и IaC. Секреты (ключи API, пароли, приватные ключи) **не храните в репозитории** — только в переменных окружения и секрет-хранилищах провайдеров.

**Полезные ссылки (уточняйте актуальные URL по документации):**

- [Oracle Cloud Free Tier](https://www.oracle.com/cloud/free/)
- [Oracle Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

---

## Фаза 0 — зафиксировать контуры

**Цель:** не начинать инфраструктуру «в вакууме».

1. **Что в проде:** список сервисов, доменов, кто пользователи (только вы или ещё кто-то).
2. **Данные:** что критично (БД, файлы, конфиги), где живут бэкапы, какой допустимый простой (RTO/RPO — прикинуть порядок).
3. **DNS:** у кого зона (Reg.ru, Cloudflare, Yandex и т.д.), текущий TTL, нужен ли низкий TTL перед сменой записей для drill.
4. **Имена и теги:** единый префикс для ресурсов (например `sauron-*`), чтобы не путать compartment’ы и VM.

Выход: короткая таблица «сервис → URL → где бэкап → ответственность».

---

## Фаза 1 — Oracle Cloud Always Free (мастер-ВМ)

**Цель:** поднять стабильную ARM-ВМ в рамках Always Free.

1. Регистрация и выбор **home region** (менять сложно; capacity по регионам разный).
2. **VCN:** приватная сеть, публичная подсеть при необходимости, маршрут в интернет (NAT/Internet Gateway — по гайдам Oracle).
3. **Security lists / NSG:** минимум открытых портов; SSH **только с ваших IP** (или через bastion/WireGuard позже).
4. **Compute:** shapes вроде **VM.Standard.A1.Flex** до **2 OCPU** и **12 GB RAM** в пределах Always Free ([документация Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)).
5. **Out of capacity:** если в регионе нет ARM — другой AD/регион или повтор позже; зафиксируйте запасной регион заранее.

Выход: работающая ВМ, SSH только с доверенных адресов, зафиксированы OCID compartment/VCN/subnet (для IaC позже).

---

## Фаза 2 — hardening и секреты

**Цель:** базовая безопасность до публикации сервисов наружу.

1. **SSH:** ключи, запрет паролей, при необходимости `fail2ban` или аналог.
2. **Firewall** на ВМ (и согласование с security lists): открывать только то, что нужно.
3. **Секреты:** не в plaintext в репо; для Terraform — remote state и backend с блокировкой; переменные через CI/CD секреты или `~/.env` локально (в `.gitignore`).

Выход: чеклист «что открыто наружу» + где лежат секреты.

---

## Фаза 3 — Uptime Kuma (мониторинг)

**Цель:** видеть деградацию до того, как «всё упало», и готовить сигналы для failover.

1. **Docker:** установка Docker на ВМ (или отдельный хост — по вашей схеме).
2. **Uptime Kuma:** контейнер, том для данных, резервное копирование тома/конфига.
3. **HTTPS:** reverse proxy (Caddy/Traefik/Nginx) с Let’s Encrypt на отдельном поддомене.
4. **Алерты:** Telegram/Email/Slack — по вкусу.
5. **Порог для failover:** сколько подряд неуспешных проверок (N fail) считаете триггером — зафиксируйте до автоматизации.

Выход: дашборд мониторинга, список проверок (HTTP/TCP), настроенные уведомления.

---

## Фаза 4 — VPN (например VLESS)

**Цель:** личный зашифрованный доступ к своим сервисам.

1. Выбор стека (Xray/VLESS и т.д.) и порты — **узко**, только необходимое.
2. **TLS:** корректные сертификаты (Let's Encrypt), обновление.
3. **Маршрутизация:** что идёт в туннель, что напрямую — на клиентах.
4. **Acceptable use:** перечитать условия Oracle и страны пребывания.

Выход: рабочий клиент на 1–2 устройствах, документ «порт/домен/протокол».

---

## Фаза 5 — воспроизводимый деплой (IaC + приложения)

**Цель:** не «единственный ручной сервер», а то, что можно воссоздать.

1. **Terraform/Ansible/Compose** — по сложности; минимум: описание ВМ, сетей, DNS-записей (где уместно).
2. **Бэкапы:** что, куда, как часто; тест восстановления хотя бы раз вручную.
3. **БД и состояние:** если есть — отдельный том/снапшоты, миграции.

Заготовки без секретов кладите в `templates/` (см. конец документа).

Выход: README в репо + команда «поднять с нуля» в несколько шагов.

---

## Фаза 6 — failover через DNS и (опционально) API

**Цель:** при падении основной площадки переключить трафик **записью DNS** (и при желании автоматизацией), а не клонированием диска «руками».

1. **Вторичная площадка:** схематично (например Yandex Cloud, другой регион Oracle) — минимальный «холодный» стенд или заранее подготовленный образ.
2. **DNS:** низкий TTL перед переключением; API провайдера DNS для смены A/AAAA/CNAME.
3. **Связка с мониторингом:** webhook от Uptime Kuma → скрипт/CI, который **меняет только DNS** (или шлёт уведомление для полуавтомата — безопаснее на первых порах).
4. **Vercel** (если используете для фронта): держите отдельно от «мастер»-ВМ; failover сайта ≠ failover API на Oracle — не смешивайте в одной записи без понимания.

Выход: runbook «шаг 1–2–3 при дауне», кто запускает (вы/скрипт), лимиты API DNS.

---

## Фаза 7 — учения (drill) и метрики

**Цель:** заранее знать, что делать в 3 часа ночи.

1. **Тестовое переключение** на staging или отдельный поддомен.
2. **Замер времени:** сколько заняло восстановление сервиса для пользователя (RTO), какие данные потеряны допустимо (RPO).
3. **Post-mortem:** короткая запись после каждого drill.

---

## Чеклист готовности

- [ ] ВМ Oracle в Always Free, SSH и firewall минимальны.
- [ ] Мониторинг с алертами и понятным порогом N fail.
- [ ] VPN работает с ваших устройств, сертификаты обновляются.
- [ ] IaC/скрипты воспроизводят деплой без ручных правок в консоли там, где возможно.
- [ ] DNS: документированы записи, TTL, доступ к API/панели.
- [ ] Failover сценарий **прогнан** хотя бы один раз (хотя бы на поддомене).
- [ ] Нет секретов в git; бэкапы проверены на восстановление.

## Что класть в `templates/`

Без секретов, только примеры:

| Тип | Пример содержимого |
|-----|---------------------|
| Terraform | `variables.tf.example`, модули сети/ВМ, backend в комментариях |
| Ansible | роли: docker, firewall, kuma |
| CI | workflow «apply при теге», с секретами из хранилища GitHub/GitLab |

Переименуйте `.example` → реальные файлы локально и не коммитьте значения с паролями.
